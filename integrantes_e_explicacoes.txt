OBJETIVO E ESCOPO
Estimar, na criação de uma ocorrência, se ela receberá pelo menos um apoio
válido de outra conta nas próximas 72 horas. Classe 1 = recebeu; classe 0 =
não recebeu. Só há rótulo após a janela completa. O ResolveAI pode sugerir
divulgação ao autor quando o modelo prevê ausência de apoio. Essa orientação
é uma regra textual baseada na classe prevista, não um terceiro modelo de IA.
Não muda o status da ocorrência e não afirma que o problema foi resolvido.
Sem prefeitura, SP156, previsão de execução de serviços ou dados reais.

UTILIZAR A INTERFACE NA APRESENTAÇÃO
1. Inicie a API pelo comando acima e abra http://127.0.0.1:5000.
2. Confira a indicação de disponibilidade da API e dos modelos na página.
   Se estiverem indisponíveis, mantenha o terminal aberto e verifique a
   mensagem; a interface não substitui um arquivo joblib ausente ou inválido.
3. Preencha as características da ocorrência e o contexto da comunidade.
   Os campos correspondem às sete entradas já documentadas neste arquivo.
   Os três campos numéricos de contexto aceitam somente faixas observadas
   no conjunto de treino. Os limites aparecem junto aos campos; valores
   externos são bloqueados, sem arredondar ou substituir o que foi digitado.
   Para a demonstração, os cenários de exemplo apenas preenchem entradas
   fictícias; as probabilidades não são fixadas no navegador.
4. Escolha Regressão Logística, Random Forest ou a comparação dos dois.
5. Execute a previsão. A interface envia POST /predict à API e mostra a
   estimativa de apoio em 72 horas, a probabilidade e a orientação retornada.
   Na comparação, cada modelo recebe uma requisição própria com as mesmas
   características. Não há votação, média ou terceiro modelo combinado.
6. Altere um cenário e execute novamente para demonstrar como cada modelo
   responde a outro contexto. Resultados podem divergir porque são modelos
   diferentes; isso não muda a seleção feita pela validação no notebook.
7. Use os detalhes técnicos opcionais da página para explicar a integração
   por JSON. A consulta GET /health continua disponível no navegador e no
   PowerShell; POST /predict continua disponível a outros sistemas.

Este formulário demonstra a previsão do projeto. Não cria contas, grava
ocorrências ou registra apoios reais. Não há banco de dados nem persistência
de relatos: o contexto é fornecido para uma simulação de abertura. Os modelos
continuam carregados do joblib e não são treinados ao usar a interface.
A identificação de dados sintéticos deve permanecer visível na apresentação.
Não use o resultado para afirmar resolução, execução de serviço público ou
validação do comportamento de moradores reais.

FAIXAS ACEITAS NA INTERFACE E NA API
- Moradores ativos: 14 a 129, contas distintas.
- Ocorrências recentes: 12 a 46, relatos.
- Histórico de apoio: 0.142857142857 a 0.75 na API; aproximadamente
  14,29% a 75% no formulário. O limite inferior exato é usado na validação;
  o texto em porcentagem é arredondado apenas para facilitar a leitura.
Dia da semana e horário mantêm 0–6 e 0–23, respectivamente.

Esses limites são os mínimos e máximos de cada entrada numérica APENAS no
treino temporal. O notebook os calcula e grava em metadados.faixas_treino no
joblib. API e interface leem os mesmos metadados, sem consultar ou recalcular
faixas pelo CSV durante o uso. Não se usam validação ou teste para ampliar
os limites. É necessário manter o joblib atualizado junto do código atual.
Valores antes aceitos pelo contrato amplo, como 200 moradores, 100% de
histórico ou 1.000 relatos, deixam de ser admitidos neste demonstrador.
A API também bloqueia requisições diretas fora das faixas com HTTP 400,
antes de executar a previsão; a proteção não depende apenas do navegador.

Essa é uma proteção contra extrapolação extrema, não uma garantia de que
o modelo foi bem treinado para qualquer combinação dos valores aceitos.
Os limites são individuais: uma combinação pode ser pouco frequente ou
não aparecer no treino. A proteção não calibra probabilidades, não assegura
acerto e não obriga os classificadores a concordarem. As limitações dos
dados sintéticos continuam valendo dentro das faixas.

CONSULTA DE SAÚDE — EM UM SEGUNDO TERMINAL POWERSHELL
    Invoke-RestMethod -Method Get -Uri 'http://127.0.0.1:5000/health' | ConvertTo-Json -Depth 5

Resposta de saúde HTTP 200 quando tudo está disponível:
{
  "api_disponivel": true,
  "dados_sinteticos": true,
  "modelos": {
    "random_forest": true,
    "regressao_logistica": true
  },
  "status": "ok"
}

POST /predict aceita exatamente dois campos no objeto JSON:
"modelo" e "caracteristicas". Não admite campos extras ou faltantes.
Modelo: regressao_logistica ou random_forest (escolha obrigatória).
Características obrigatórias:
- categoria: iluminacao, limpeza, vias ou acessibilidade (texto exato).
- regiao: norte, sul, leste ou oeste (regiões fictícias; texto exato).
- dia_semana: inteiro 0–6; segunda = 0, domingo = 6.
- hora_abertura: inteiro 0–23, horário local de São Paulo.
- moradores_ativos_7d: inteiro de 14 a 129, contas distintas com sessões na
  região em [abertura - 7 dias, abertura). A simulação tem 200 contas por
  região, mas a API restringe a entrada à faixa efetivamente vista no treino.
- taxa_apoio_anterior_28d: número finito de 0.142857142857 a 0.75. É uma proporção,
  não o percentual exibido no formulário. Na mesma região e categoria,
  considerar aberturas a partir de abertura - 31 dias e somente janelas de
  72 horas encerradas ANTES da abertura atual. Usar (2 + positivos)/(4 + total).
  Sem histórico, usar 0.5. O intervalo de aberturas maduras cobre 28 dias.
- ocorrencias_regiao_7d: inteiro de 12 a 46, aberturas na mesma região nos sete
  dias anteriores, excluindo a atual; não indica situação de resolução.
Booleanos, números entre aspas, contadores com casas decimais, NaN/Infinity e
chaves JSON repetidas são rejeitados. As faixas observadas no treino são
validadas no servidor, mas não garantem a representatividade da combinação.
O sistema integrador deve calcular os históricos com dados anteriores; a API
verifica o formato e os limites, mas não consulta um banco nem audita sua origem.

CÓDIGOS HTTP
200: consulta ou previsão realizada.
400: JSON malformado, campo faltante/extra, modelo ou valor inválido, inclusive
característica numérica fora da faixa de treino; a mensagem informa o limite.
404: rota inexistente; 405: método não permitido.
413: corpo acima de 16 KiB; 415: Content-Type diferente de JSON.
503: arquivo de modelos ausente, corrompido ou incompatível.
500: falha inesperada ao executar a inferência (mensagem JSON genérica;
detalhes no terminal do servidor).
Com modelo ausente/incompatível, /health continua acessível com status 503,
api_disponivel=true e os dois modelos indisponíveis. Uma previsão válida
também retorna 503. Restaure o arquivo entregue e instale requirements.txt.
O joblib usa componentes padrão, sem classes personalizadas ou caminhos
pessoais. A API exige as versões de numpy/pandas/scipy/scikit-learn/joblib
registradas no treinamento. Carregue apenas artefatos joblib confiáveis.

DADOS, HIPÓTESES E AUSÊNCIA DE VAZAMENTO
Uma ocorrência por linha, dados locais fictícios. 4.000 aberturas sorteadas de
01/12/2025 a 31/07/2026; dezembro apenas aquece os históricos. O CSV possui
3.458 linhas, todas com observação completa até a extração de 04/08/2026.
Semente única: 20261112. Não se gerou cada classe separadamente.
Exposições futuras seguem Poisson com efeitos inventados de atividade,
categoria, horário, fim de semana e competição entre relatos. Atenção futura
lognormal representa variação não observada. Uma exposição pode gerar uma
tentativa de apoio até 96 horas; somente os apoios válidos até 72 horas
produzem classe 1. Não se trocaram rótulos nem se adicionou ruído ao alvo.
Conta autora, conta não habilitada e apoio duplicado à mesma ocorrência não
valem. Tentativas são processadas em ordem de tempo por ocorrência.
Os contadores olham apenas para o passado. A taxa histórica lê somente
resultados com janela já encerrada. Probabilidade interna, atenção futura,
contas e eventos de apoio ficam fora das entradas da API e do CSV.
O dicionário completo, código gerador e auditoria por eventos estão no notebook.

Separação fixa: treino 2.215 linhas, validação 598, teste 555. Outras 90 linhas
ficam nos intervalos de maturação. O último resultado do treino já é conhecido
antes da primeira abertura de validação; o mesmo vale de validação para teste.
Não se misturam registros entre conjuntos. No uso sequencial simulado, os
históricos são atualizados com eventos passados, sem retreinar os modelos.
Pré-processamento aprendido apenas no treino, dentro de cada pipeline.
Nenhum ajuste do gerador foi feito para atingir uma métrica ou favorecer modelo.
Os filtros de entrada foram acrescentados para evitar extrapolação extrema
na apresentação. Nenhum registro foi recortado, alterado ou removido do CSV
por causa deles. A exportação reproduzível passou a registrar as faixas de
treino; algoritmos, configurações, semente e critério de seleção permanecem
os mesmos. Os classificadores não foram ajustados para concordar entre si.

RESULTADOS EFETIVAMENTE OBTIDOS
Critério prévio: F1 macro na validação, limiar 0.5 e configurações fixas.
Regressão Logística é um classificador, apesar do nome. Random Forest também
é de classificação. DummyClassifier é somente a referência, não um dos dois
modelos exigidos. Os candidatos foram exportados sem retreino após seleção.

Modelo                 | F1 val | F1 teste | Acurácia teste | Brier teste
referencia_dummy       | 0.3618 | 0.3584 | 0.5586 | 0.2468
regressao_logistica    | 0.5715 | 0.5879 | 0.6126 | 0.2360
random_forest          | 0.5398 | 0.5948 | 0.6360 | 0.2327

A Regressão Logística foi escolhida pela validação (diferença de F1 macro
aproximadamente 0.0317). No teste, a Random Forest teve F1 macro maior por
aproximadamente 0.0070: diferença pequena, sem demonstração de significância.
A ordem invertida no teste não muda a escolha anterior. Ambos superaram o
Dummy em F1 macro neste teste. Precisão, recall, F1 e suporte por classe,
matrizes de confusão, probabilidades e importância por permutação estão no
notebook. Brier menor é melhor; não prova calibração fora da simulação.
As métricas acima são da avaliação original no conjunto de teste completo.
O filtro da API é uma regra adicional de admissibilidade de entradas; não
constitui nova avaliação, recalibração ou melhoria comprovada das métricas.
No treino, houve 252 casos sem apoio entre os relatos de atividade alta e
177 com apoio entre os de atividade baixa (quartis superior e inferior).
Foram encontrados 117 grupos com pelo menos cinco contextos aproximados e
ambos os resultados. Não houve separação perfeita das classes.

LIMITAÇÕES
Os parâmetros são inventados e nenhum registro representa moradores reais.
Métricas não comprovam desempenho em uso real, nem efeito causal da sugestão.
Uma semente e uma partição temporal não demonstram superioridade geral.
Históricos e sessões compartilhados criam dependências entre ocorrências.
Falso positivo: prever apoio que não vem pode omitir uma sugestão útil.
Falso negativo: prever ausência quando houve apoio pode sugerir divulgação
desnecessária. Não apoiar não significa irrelevância ou falsidade do relato.
Atividade e região podem refletir desigualdade digital. Antes de uso real:
obter dados com governança, testar outros períodos e comunidades, avaliar
calibração e vieses e acompanhar mudanças. Esta entrega não realiza isso.
A interface local foi acrescentada para demonstrar os modelos usando a API.
Não há chatbot, banco, Docker, nuvem, visão computacional ou previsão de
resolução. O servidor demonstrativo é local e sem autenticação.
Mesmo dentro dos mínimos e máximos do treino, combinações raras e relações
inventadas podem produzir probabilidades diferentes ou previsões erradas.
Estar dentro das faixas não comprova qualidade preditiva com moradores reais.
